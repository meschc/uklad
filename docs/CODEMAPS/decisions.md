# Ключевые решения — подробно

Полный текст решений, на которые коротко ссылается `CLAUDE.md`. Почему —
в `docs/adr/`, как устроено по файлам — в соседних картах.

- **Две сборки, а не одна** (`index.html` → `src/site`, `app/index.html` →
  `src/main.tsx`). Общее — токены темы, `cn` и примитивы `ui/`; маршрутизация,
  словарь и данные у половин свои. Витрина ходит по настоящим путям и
  предрендерится в статику (156 страниц), кабинет переключает экраны полем
  стора `appView`. Роутера нет ни там, ни там — см. `docs/adr/`. Кабинет
  живёт по `/app/`: переезд на поддомен `app.u-klad.ru` (ADR 0008) владелец
  отложил 7 октября 2026. Сборка под поддомен готова — `npm run build:app`
  собирает кабинет один с корнем `/`. Из кабинета на витрину ведёт одна ссылка —
  «Посмотреть на витрине» в паспорте склада (предпросмотр `/warehouse/preview/`
  читает то же сохранение, `site/lib/cabinetShowcase.ts`); после переезда на
  поддомен её заменит карточка по API. Других ссылок не добавлять.
- **Одна дизайн-система на витрину и кабинет** (ADR 0007). Токены — только в
  `src/index.css`, примитивы — `src/components/ui/`; витрина добавляет поверх
  характер (скругления `--r`, ритм длинной страницы), но не свою палитру и не
  свои высоты. Своих кнопок и надзаголовка у витрины тоже нет: действия —
  `ui/button` с `shape="pill"`, главный призыв — `CtaLink` поверх неё,
  надзаголовок — `ui/eyebrow` тоном `primary`. Описание для людей
  вне кода — артефакт
  https://claude.ai/artifact/Tadqydujk1gJrKcysRePzm, правится вместе с кодом
  (см. «Соглашения»).
- **Данные только в localStorage**, ключ `uklad-store-v1`, версия персиста 8.
  Сохранение сжато (`lib/storeCodec.ts`) и пишется не чаще раза в секунду
  (`store/persistStorage.ts`); мимо стора — только `writeSaved`/`removeSaved`/
  `readSaved`, сырой `localStorage.getItem` его не прочитает.
  Второй «аккаунт» (продавец) — это режим просмотра тех же данных, а не сеть.
- **Весь доступ к данным — через `lib/data/*Repository.ts`**, а не напрямую в
  localStorage. Сегодня внутри тот же Zustand, сигнатуры уже асинхронные:
  когда придёт Supabase, меняется реализация репозитория, а не экраны. Реактивный
  рендер по-прежнему подписан на стор — он и есть локальный кэш. На границе
  хранилища (`merge` в `store/index.ts` → `data/sanitize.ts`) каждая доменная
  запись проходит проверку формы: битая запись теряется одна, а не роняет
  приложение.
- **Роль читается только из сессии** (`selectRole(s)` → `session.user.role`).
  Отдельного поля `currentRole` больше нет: `User`/`Session` описаны так, чтобы
  стать настоящей авторизацией без правки экранов. Сборка с сервером
  (`VITE_API_URL=/api`, образ `deploy/web.Dockerfile`) входит паролем через
  `server/api` (`authRepository`, `ServerLoginForm`): токен в куке `HttpOnly`,
  в сторе только `session.source = "server"` и компания. Демо на GitHub Pages
  собирается без адреса и входит по-старому, локальным моком. Данные кабинета
  компании живут на сервере одним снимком (ADR 0010, `store/serverSync.ts`,
  `uklad.cabinet_snapshots`): при входе сервер главнее, новая компания
  начинает с пустого склада, правки уходят сами, запись только поверх
  известной версии. Снимок раскладывается по таблицам по шагам: товары уже
  не в нём (миграция 013, `uklad.products`) — кабинет шлёт и получает их в
  составе снимка, сервер хранит строками с корзиной и журналом правок.
  Работа склада — тоже строками (миграция 021, `cabinet/records.js`,
  `uklad.cabinet_records`): заявки, поставки, приёмка, тара, рейсы, задания,
  спорное, документы и журнал смен; в документе от них метки `$rows`.
  Руководитель пишет только изменённое (`data/cabinetRows.ts`,
  `/api/cabinet/snapshot/changes`), не сошлось — `diverged` и запись целиком.
  Законченное старше 45 дней сервер уводит в архив (миграция 022,
  `archiveRecords`): кабинет и стол его не получают, запись его не трогает.
  Отчёты за долгий период подмешивают архив из памяти — `useWithArchive`
  (`store/archive.ts`, `GET /api/cabinet/history`) вместо `useEditor`.
  Каждая запись снимка (кабинет и стол) дописывает журнал движений
  (миграция 014, `cabinet/moves.js`, `uklad.stock_moves`): сколько какого
  товара прибыло и убыло в таре, коробе отгрузки и ячейке и кто записал.
  Переключение склада движением не считается.
  Стол пишет работу операциями (миграция 015, `cabinet/deskOps.js`,
  `data/opQueue.ts`): факт с ключом повтора, сервер сам кладёт его в снимок
  и в `uklad.desk_ops`, за кого — решает сам (названный столом сотрудник
  должен быть за столом). Очередь на устройстве переживает обрыв и
  перезагрузку, неотправленное видно в шапке. Так ходят отметки смены и
  упаковка (`cabinet/deskPack.js`, миграция 016): стол шлёт факты закрытия
  тары, сервер сам повторяет правку и пропускает её через `mergeDeskWrite`.
  Брак при упаковке остаётся в таре спорным «не подлежит упаковке» —
  решения по товару принимает только старший. Сборка — так же
  (`cabinet/deskPick.js`, миграция 017): «штука с этого места в эту тару
  под эту заявку» и «заявка собрана»; сервер сам снимает с места, кладёт в
  тару и пишет `pick_scan` в журнал сотрудника.
  Приёмка — так же (`cabinet/deskReceive.js`, миграция 018): вскрыть место,
  принятое в тару, тара в ячейку и на паллету, поставка принята. Кроссдок
  решает поставка на сервере; новых тар стол на сервере не заводит, а места
  грузовой приёмки (`recv_cargo`, миграция 020) заводит и нумерует сервер —
  ярлыки стол печатает по его ответу.
  Принятое сверх строки или без поставки сервер помечает `overage` и сам
  заводит спорным «Лишнее с приёмки» (`receive_overage`): старший оставляет
  его на складе или списывает — вернули поставщику.
  Рейс (`ship_run`) и решение старшего по спорному (`dispute_resolve`) —
  тоже операциями (`cabinet/deskShip.js`, миграция 019).
  Браузер держит копию: любой 401 закрывает кабинет экраном
  входа, данные не трогая (`sessionLost`); в сборке с сервером кабинет без
  входа закрыт целиком, демо — только по заявке. Стирает копию
  (`store/leave.ts`) выход — сразу, если всё записано, иначе с «Скачать
  копию».
- **Экран падает один**: каждый вид обёрнут `ErrorBoundary` (ключ по виду, см.
  `App.tsx`). Изолируем сбой рендера, а не данные: единый `buildOccupancy`
  остаётся один на всех.
- **План условный**: координаты модулей — в КЛЕТКАХ сетки, реальные см живут
  отдельными полями и на визуальный масштаб не влияют.
- **«Пол как проход»**: объектов-проходов больше нет, зазор между линиями
  секций и есть проход (миграция v1→v2 вырезает `type: "aisle"`).
- **Связанные этажи** (`Floor.aliasOf`): этаж-алиас зеркалит раскладку
  источника, правки уходят в источник — см. `resolveFloor` / `mutateActiveFloor`.
- **Единый alert-паттерн** «на полке товар» (`GoodsConflictDialog`): правку
  плана не запрещаем, а спрашиваем, что делать с товаром.
- **Сканирование — HID** (сканер «печатает» код + Enter), без камеры.
- **Приёмка идёт от тары**: паллета (необязательно) → открыть тару → товар →
  закрыть тару и поставить на место. Ярлыки тары печатаются заранее на экране
  «Ярлыки», приёмка их только сканирует.
- **Одна высота на строку интерфейса**: контролы только трёх ступеней —
  32 / 36 / 40 px (`Button`, `Input`, `Segmented`). Любые «кнопки-табы» — через
  `ui/segmented.tsx`, свои наборы `bg-muted p-0.5` не собираем.
- **Профиль правится по одному полю**: карандаш открывает одну строку,
  галочка сохраняет её (Enter/Escape тоже работают). Почта меняется только
  через подтверждение кода, реквизиты компании приходят по ИНН сами — кнопки
  «подтянуть» нет.
- **Регистрация — почта и пароль**: имя и компания живут в профиле, а не в
  пропуске в систему. Роль (склад/продавец) в форме остаётся: она решает, куда
  человек попадёт после входа.
- **Заявки группируются по назначению**: одна машина увозит всё, что едет
  одному получателю; дата отгрузки — подпись к группе, а не её ключ.
- **Нагрузка персонала — по фактам, а не по ощущениям** (`staffWorkload`):
  приёмки, принятые единицы, отгрузки и дата последней операции берутся из
  `ReceivingEvent.staffId` и `Shipment.staffId`. Сборка персонально не
  подписывается, поэтому в нагрузку не входит — числа, которого нет в данных,
  в таблице быть не должно.
- **Паспорт склада — один экран на две роли** (`WarehouseSpecScreen`, вид
  `spec`): режим работы и заезд, условия хранения (температура, влажность),
  противопожарная категория и оснащение, ограничения и состояние. Склад правит
  поля на месте, продавец видит те же данные на чтение — второй «витрины»
  нет по той же причине, что и у таблицы номенклатуры.
- **Машину может назвать продавец**: поле в заявке (`vehicle`), склад видит его
  подставленным в диалоге погрузки и только подтверждает.
- **У продавца два направления, а не одно**: «В заявку» — забрать со склада,
  «Везу товар» (`SupplyDialog`) — привезти на склад. Второе создаёт обычную
  ожидаемую поставку (`createExpectedShipment`, источник `manual`), которую
  склад принимает построчно со сверкой план/факт; продавец видит её прогресс
  блоком «Еду на склад».
- **«Собрана» и «отгружена» — разные статусы**: снятое с полок ещё не уехало.
  Погрузка — отдельный шаг (`shipRequests`, `ShipDialog`): собранные заявки
  одного назначения уезжают рейсом (`Shipment`) с номером машины и
  ответственным. Продавец в своих заявках видит «Уехало {дата} · машина» —
  это и есть отчёт подрядчика о выполненной работе.
- **Роль продавца — режим чтения**: те же план, номенклатура и персонал, но без
  структурных правок — ни «плюсиков» продолжения ряда, ни контекстного меню,
  ни горячих клавиш, ни undo, ни создания складов. Проверка роли — в трёх
  местах: `useShortcuts`, `Canvas`, `Dashboard`; экраны прячут своё через
  `readOnly = currentRole === "seller"`. Заявка набирается списком позиций на
  одну машину.
- **Одна таблица номенклатуры на обе роли**: у продавца на вкладке «Остатки»
  та же `TableScreen`, только без складских действий и с «В заявку». Своя
  урезанная копия таблицы разъезжается с настоящей на первой же правке.
- **Запрет висячих строк**: короткие слова и числа склеиваются неразрывным
  пробелом в `i18n.ts` (`noOrphans`), последнюю строку абзаца балансирует CSS
  (`text-wrap: pretty` / `balance` в `index.css`). Работают только вместе.
- **Кроссдокинг и дропшиппинг — две стороны одного «товара, которого ещё нет»**:
  у поставки с `crossDock` шага «место» нет вовсе, принятое сразу закрывает
  ждущие заявки (`applyCrossDock`) и в занятость не попадает — оно физически не
  хранится. Обратно: заявка бронируется под ещё не приехавшую строку поставки
  (`reservedFor` / `reservedShipmentId`); свободное для брони — это ожидаемое
  минус принятое минус чужая бронь, иначе одну коробку продадут дважды.
- **Наборов нет**: убраны из продукта миграцией v6 → v7 (`store/index.ts`).
- **Приоритет отбора живёт на полке** (`ShelfConfig.pickPriority` / `pickable`):
  меньше число — ближе к проходу и раньше в автоподборе; `pickable: false`
  исключает полку из подбора, не трогая то, что уже лежит.
- **Тарифы сайта — закон для кабинета** (`lib/tariff.ts`, `TARIFF_FEATURES`):
  «Старт» видит в аналитике только верхний ряд чисел, менеджер — только у
  «Оператора», копия на почту — у «Склада» и «Оператора». Тест сверяет таблицу
  с `warehouses/tariffsData.ts`: поменял галочку на сайте — поменяй кабинет.
  Тариф пока выбирается в профиле, оплаты нет.
- **Резервная копия — это `persistedState` одним файлом** (`lib/backup.ts`,
  `backupRepository`): восстановление пишет архив в хранилище персиста и
  перезагружает страницу, чтобы он прошёл те же миграции и проверку формы.
  Копия на почту — шов под сервер: сегодня хранится только согласие.
- **Рабочее место — по бейджу, а не по логину** (`WorkstationScreen`, вид
  `workstation`, срез `workstation.slice`): общий экран у стола, сотрудник
  сканирует QR-бейдж (`UK-STF-<id>`), вход живёт 12 ч. Меню смены (смена,
  перерыв, часы, заработок по `hourlyRate`) одно на стол, ТСД и телефон.
  Журнал (`staffEvents`) пишется только по действиям человека — отметки,
  сканы, упаковки; время отметок — до секунды. Часы считаются по переходам
  (`workedMs`), перерыв в работу не входит. Пока сделан стол упаковки.
  **Сборка идёт в тару**: перед первым местом сборщик сканирует пустую тару
  (`UK-BOX-` без места хранения), снятое с полки ложится в неё, заявка
  помнит тару (`toteId`). В одной таре — один продавец и одно назначение
  (`pickToteProblem`), иначе на упаковке её не разложить по коробам.
  **Упаковка идёт от тары** (`lib/packing.ts`): скан тары с товаром (короб
  `UK-BOX-`) → скан короба отгрузки (`UK-OUT-`) → по каждой штуке «скан
  товара → этикетка печатается сама → скан этикетки». Следующий товар не
  берётся, пока этикетка не отсканирована. Тара с заказами (FBS/DBS):
  штука сама находит свой заказ, заказ из нескольких штук закрывается
  этикеткой заказа; без заказов (FBO) — этикетка на каждую штуку. Брак,
  «нет в таре» и лишнее — в отказы, недостача при закрытии тары остаётся
  в таре.
  **Бейдж**: в демо он из id сотрудника и подделывается копией. Вошли паролем
  на сервер — в QR случайный секрет 128 бит (`uklad.desk_badges`, миграция
  010, `cabinet/deskBadges.js`): выпускает его руководитель в «Персонале»,
  код виден один раз, новый гасит старый, удаление сотрудника гасит бейдж.
  Сервер по скану называет сотрудника (`badgeRepository`, `openStation`);
  демо-бейджи и демо-коды тары прячет `useDemoHints`. **Стол — свой пропуск,
  а не вход руководителя** (миграция 011, `cabinet/desks.js`,
  `data/deskServer.ts`): заведённое на сервере устройство гасит вход
  руководителя в этом браузере и получает куку стола. Стол читает снимок без
  ставок, контактов, переписки и чужих складов, пишет только работу склада
  и только операциями (`POST /api/desk/ops`): снимок кабинета стол не пишет
  вовсе — запись снимка и «только изменённое» отвечают 403. Свежее стол
  подтягивает сам (`GET /api/desk/version` раз в 20 с, `serverSync.ts`, без
  перезагрузки и только при пустой очереди), а операцию, которую сервер не
  принял или потерял, догоняет `resyncDesk`: серверная копия главнее. Журнал
  смен только дописывается, решённое спорное не меняется; в остальной
  кабинет стол получает 403. Рабочее место под входом руководителя (не стол)
  работу по-прежнему пишет снимком. **Кто за столом, знает сервер** (миграция 012): узнанный
  бейдж запоминается в пропуске стола на 12 ч, выход со стола
  (`/api/desk/leave`) его снимает, прежний сотрудник принимается ещё 10 мин.
  Отметки смены и новое спорное стол пишет только за того, кто за ним;
  решить спорное может только старший за столом (`SENIOR_ROLE`, как в
  кабинете) и от своего имени, списание — не тот, кто нашёл.
  Заявки стол не заводит и не удаляет, а в существующих меняет только ход
  работы (`REQUEST_WORK`): товар, количество и назначение неизменны. **Остатки
  со стола сверяются** (`cabinet/deskStock.js`, итог каждой операции идёт через
  `mergeDeskWrite`): по каждому товару ушедшее
  из тары должно уйти в собранное, короб отгрузки, списание или снятое
  размещение, а прирост — прийти приёмкой за того, кто за столом. Приёмка,
  рейсы и уехавшие короба только дописываются, ставить товар в ячейку стол
  не может. Не сошлось — операция помечается `flagged` (`stock`), товар не
  двигается, стол забирает серверную копию; отметки смены остаются. Таблицы остатков заменят сверку, когда товары переедут на
  сервер.
  Журнал и ставку видят только сотрудник и руководитель.
- **Каждая операция — услуга со следом** (`lib/operations.ts`, экран
  «Операции»). Склад сам включает, что оказывает, и задаёт цену за единицу.
  Приёмку паллет, коробов и штук, сборку и рейсы журнал берёт из фактов сам;
  остальное (маркировка, ЧЗ, упаковка, возвраты…) — заданием, датой услуги
  считается закрытие. Журнал не хранится, а собирается (`operationLog`), отчёт
  без цены показывает «—», а не ноль. Выключенная услуга в счёт не идёт.
- **Приёмка в два этапа — режим склада** (`serviceSettings.twoStageReceiving`,
  `lib/cargo.ts`). Грузовая: места по накладной и по факту при водителе,
  каждое место — невскрытая паллета или короб (`sealed`, `shipmentId`) со
  своим ярлыком; машин может быть несколько, факт копится. Товарная: место
  вскрывают сканом или со списка «ждут вскрытия», дальше обычный мастер.
  Сквозной сценарий склада — `store/__tests__/warehouse.flow.test.ts`.
- **Команда и роли — действия на сервере** (миграция 023,
  `server/api/src/cabinet/team.js`, вкладка «Доступ» в «Персонале»). Второй
  человек входит под своей почтой по ссылке из письма (`/app/#invite=…`, токен
  во фрагменте, в базе хэш, 7 дней, одноразовая). Правила в базе, а не в
  экране: роль можно дать, только если все её права есть у самого делающего;
  выше себя и себя самого не переназначить и не отключить (отсюда владелец
  остаётся всегда); своя роль не включает `org.manage`; роли по умолчанию не
  правятся. Управляет командой право `staff.manage` при входе паролем. Пока
  снимок кабинета целиком доступен только `staff.manage` (начальник и
  владелец): кладовщик с входом по почте кабинет не откроет, он работает
  у стола по бейджу. Права на чтение и запись по доменам — вместе с переносом
  снимка в таблицы.
- **Права у стола — по роли, а не по должности** (миграция 024,
  `server/api/src/cabinet/deskPerms.js`). Сотруднику стола (строка
  `warehouse.staff`) руководитель назначает роль во вкладке «Доступ»
  (`uklad.desk_staff_roles`, `auth.set_desk_staff_role`, те же правила, что у
  команды). Стол спрашивает права роли: приёмка, сборка, упаковка, отгрузка —
  `*.do`, решения по спорному — `goods.decide`, отвязка стола —
  `staff.manage`. Без роли работа идёт как раньше, а решений нет (иначе стол
  встал бы у всех, кому роль ещё не назначили). Ответ на бейдж несёт права
  роли, и экран споров у стола спрашивает то же право (`mayDecideGoods`); по
  должности (`isSenior`) решают только демо и подтверждение документов в
  кабинете — до их переноса на сервер. Права по модулям и где они уже
  действуют — `src/lib/permModules.ts`, таблица «роль × модуль» в «Доступе».
- **Кабинет для ролей без «Персонала» — только просмотр.** Член команды с
  `stock.view`, но без `staff.manage` и без `seller.requests` (кладовщик,
  приёмщик…), получает снимок по разрешённому списку (`cabinet/viewer.js`:
  без реквизитов, тарифа, цен, ставок, контактов, журнала смен, переписки) с
  пометкой `viewer`; тест сверяет список с сохраняемыми ключами браузера, так
  что новое поле закрыто по умолчанию. Запись снимка — только `staff.manage`. В браузере `session.readOnly` и `readOnlyGuard.ts`:
  одно место на весь стор не даёт правке компании лечь даже локально.
  Участок человека — по журналу смен (`staffProcess.ts`), права от него не
  меняются.
- В dev доступен `window.__uklad` — стор целиком, для проверки сценариев из
  консоли вместо ручной пантомимы мышью.
