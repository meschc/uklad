# Разработка

Как поднять проект, какие есть команды и проверки, как он устроен. Раньше это
лежало в README; README теперь короткий. Правила веток и коммитов —
[CONTRIBUTING.md](../CONTRIBUTING.md).

## Запуск

```bash
npm install
npm run dev
```

Откроется на `http://localhost:5174` (порт закреплён) — на сайте; демо
рядом, на `http://localhost:5174/app/`. При первом запуске подсевается
демо-склад: каталог товаров, персонал, поставки, заявки и рейсы за последние
70 дней — чтобы экраны были живыми, а не пустыми формами.

## Скрипты

| Команда                | Что делает                                      |
| ---------------------- | ----------------------------------------------- |
| `npm run dev`          | дев-сервер на 5174                              |
| `npm run build`        | типы, сборка в `dist`, предрендер 26 страниц    |
| `npm run build:app`    | один кабинет в `dist-app` — под `app.u-klad.ru` |
| `npm run preview`      | посмотреть собранное                            |
| `npm run lint`         | ESLint по всему проекту                         |
| `npm run lint:fix`     | он же с исправлениями                           |
| `npm run typecheck`    | `tsc -b --noEmit`                               |
| `npm run format`       | Prettier по всему проекту                       |
| `npm run format:check` | проверить формат, ничего не меняя               |
| `npm test`             | Vitest, разово                                  |
| `npm run coverage`     | тесты с покрытием                               |
| `npm run test:e2e`     | сквозные тесты Playwright по собранному сайту   |
| `npm run test:e2e:ui`  | они же в интерактивном режиме                   |
| `npm run tokens`       | пересобрать токены дизайна из `src/index.css`   |

## Проверки

Три рубежа, от быстрого к полному:

- **перед коммитом** — `lint-staged` прогоняет ESLint и Prettier по файлам в
  индексе. Секунда работы; правила в `lint-staged.config.js`;
- **перед `git push`** — `npm run typecheck` и `npm test`. Это то, что нельзя
  проверить по одному файлу;
- **в CI** — `.github/workflows/ci.yml`: формат, линтер, типы, тесты, сборка и
  отдельным заданием сквозные тесты на чистой машине.

Хуки ставит [husky](https://typicode.github.io/husky/) — сами, при `npm install`.
Обойти проверку осознанно: `git commit --no-verify`, `git push --no-verify`.

**Покрытие — 55 % по строкам и 86 % по ветвлениям** (`npm run coverage`),
считается по всей логике: `src/lib`, `src/site/lib`, `src/site/data`. Цифра
настоящая, а не подогнанная: закрыты раскладка товара, жизненный цикл заявки,
чат, маршруты и мета витрины, разбор адреса, посев демо-данных — то, где ошибка
стоит дорого и незаметна. Не закрыты репозитории поверх `localStorage`, справочник
интеграций, сцена 3D и срезы стора вокруг редактора плана: там ошибка видна сразу
на экране. Ветвления закрыты вдвое лучше строк — так и задумано: проверяются
развилки, а не проход по коду.

Экраны (`.tsx`) в подсчёт не входят: их проверяют компонентные тесты и
Playwright, а сквозной прогон в этот отчёт не попадает — смешивать их значило бы
получить цифру, которая тем ниже, чем лучше работает Playwright. Порога, ниже
которого сборка падает, нет намеренно: он заставляет писать тесты ради процента,
а не ради проверки.

## Стек

React 18 + TypeScript, Vite (две точки входа), Zustand (срезы + `persist`),
Tailwind и shadcn/ui, Vitest и Playwright. Leaflet — карта на витрине. Три.js —
под флагом, для 3D-вида плана.

## Архитектура в трёх абзацах

**Две сборки, а не одна.** Vite собирает MPA: `index.html` → `src/site` (витрина),
`app/index.html` → `src/main.tsx` (кабинет). Общее у половин — токены темы, `cn`
и примитивы `ui/`; маршрутизация, словарь и данные у каждой свои. Иначе лендинг
тянул бы ради первого экрана редактор плана и three.js. Роутера нет ни там, ни
там: сайт ходит по настоящим путям (`/warehouses/`, `/pricing/`, `/en/`) из
списка `src/site/lib/routes.ts`, кабинет переключает экраны полем стора
`appView` — рабочим местом на смену ссылками не делятся. Кабинет собирается и
отдельно, под поддомен `app.u-klad.ru` (`npm run build:app`,
[ADR 0008](adr/0008-kabinet-na-poddomene.md)). Дизайн-система у половин
одна ([ADR 0007](adr/0007-odna-dizajn-sistema.md)): токены в
`src/index.css`, примитивы в `ui/`, описание — в `docs/design/`.

**Экран не ходит в хранилище сам.** Между ними слой `src/lib/data/`: репозиторий
поверх порта `StorePort { get, set }`, ответ в конверте `Result<T>`, вызов через
`useCommand` → `{ run, pending, error, reset }`. Ошибка возвращается ключом
словаря, а не готовой фразой. Смысл в том, что появление сервера — замена одной
реализации порта, а не переписывание экранов: ожидание и ошибка на экранах уже
нарисованы, хотя сейчас всё отвечает мгновенно. Исключение одно и объяснено —
репозиторий складов на витрине синхронный, потому что предрендер не умеет ждать.

**Витрину читает робот.** Она не одностраничник в реальности: `npm run build`
дорисовывает статику — 26 файлов (13 адресов × два языка) и `sitemap.xml`, у
каждой страницы свой `<title>`, описание, канонический адрес, языковые
`alternate` и разметка Schema.org. Переводов два комплекта: в кабинете словарь с
`MsgKey`, где забытый перевод не проходит сборку, на витрине — пары `c(ru, en)`
рядом с вёрсткой.

Развёрнуто — [docs/ARCHITECTURE.md](ARCHITECTURE.md); почему выбрано именно
так, с ценой каждого решения — [docs/adr/](adr/).

## Структура

```
index.html         вход сайта; app/index.html — вход демо WMS
src/site/          лендинг, витрина складов, тарифы, правовые документы
src/components/    экраны и UI демо; fulfillment/ — приёмка, сборка, отгрузка
src/lib/           доменная логика: placement, address, barcode, i18n
src/lib/store/     стор по срезам (17 штук), история правок, посев демо-данных
src/lib/data/      репозитории: сервер или localStorage в демо — экраны туда не ходят сами
e2e/               сквозные тесты Playwright
scripts/           предрендер витрины, сборка кабинета под поддомен, токены
server/api/        сервер: вход, кабинет компании, стол, админка; Postgres с RLS
server/db/         миграции и тесты изоляции компаний
server/leads/      старый приёмник заявок, функция Яндекс Облака, вне сборки
deploy/            Docker и Caddy
docs/CODEMAPS/     карты кода: витрина, компоненты кабинета, стор, домен
docs/adr/          решения с ценой: сервер и Postgres, MPA, свой словарь и чат
docs/design/       дизайн-система и разбор знака: BRAND.md
public/brands/     логотипы вендоров для списка интеграций
```

Подробности по правилам работы со стором и историей — в [CLAUDE.md](../CLAUDE.md) и
`docs/CODEMAPS/`.

## Тесты

```bash
npm test
```

Основное — расчёты, которые ошибаются молча: занятость ячеек, подбор места,
бронь под поставку, кроссдокинг, сборка заявки. Неверный ответ в этих местах
выглядит как обычный, и заметить его можно только по расхождению через неделю.

Сверх них — компонентные тесты в jsdom, по одному файлу на место, где ломается
не расчёт, а поведение: галочки согласий (152-ФЗ: два раздельных поля, оба
пустые до нажатия), заявка складу на витрине (без согласия на обработку данных
кнопка не работает), категории товаров (занятое имя, сбой связи и повтор) и
мастер приёмки (порядок шагов, пропуск паллеты, отсутствие шага «место» у
кроссдока, видимый ответ на удачный скан). Окружение просится в самом файле —
строкой `// @vitest-environment jsdom` в шапке; по умолчанию тесты идут в node,
он быстрее.

```bash
npm run test:e2e
```

Сквозные — Playwright, три прогона: широкий экран, Pixel 7 и узкий телефон в
375 точек (на нём проверяется только вёрстка — то, что ломалось именно там).
Проверяются пути, которыми ходит человек: лендинг → витрина → карточка склада →
заявка, семь правовых документов по прямым ссылкам, выбор cookie и согласия под
формами, отсутствие горизонтальной прокрутки на каждой странице. Демо
`/app/` проверяется отдельно — коротким маршрутом «список складов → склад →
раздел».

Прогон идёт по **собранному** сайту на порту 4174, а не по дев-серверу. Причин
две. Ломается обычно сборка: сайт и демо собираются двумя входами
(`build.rollupOptions.input`), и «`/app/` открывается» — утверждение о
результате `vite build`, а дев-сервер про MPA ничего не знает. И порт: на 5174
живёт дев-сервер с настоящим планом склада в `localStorage`, а тесты чистят
хранилище своего origin — совпадение портов означало бы, что прогон тестов
стирает рабочие данные.

Первый запуск требует браузера: `npx playwright install chromium`.

## Оговорки

Витрина и демо на GitHub Pages — без сервера: данные там живут в браузере и
чистятся вместе с ним. Боевой кабинет работает с сервером.

Склады, цены и рейтинги на витрине сгенерированы. Реквизиты владельца в
[src/site/data/org.ts](../src/site/data/org.ts) — демонстрационные, и подобраны так,
чтобы не могли принадлежать никому: у ИНН и ОГРНИП неверные контрольные разряды и
несуществующий код региона `00`, у индекса — недопустимая первая цифра, у
телефона — невыделенный код `200`. Случайные числа для этого не годятся, они как
раз попадают в чей-нибудь настоящий ИНН; разбор арифметики — в шапке файла. Пока
`ORG.filled` равен `false`, правовые страницы печатают короткую пометку об этом;
после подстановки настоящих реквизитов достаточно поднять флаг, и пометка
исчезнет везде разом. Домен — единственное исключение из этой демонстрационной
россыпи: `u-klad.ru` настоящий, потому что от него считаются канонические
адреса и карта сайта, а заглушка там означала бы не «ещё не решили», а ошибку
в выдаче. Вписан он в двух местах: строка `Sitemap:` в `public/robots.txt` и
поле `site` в том же `org.ts`. Больше нигде — `sitemap.xml` собирается на
сборке из этого же поля.

Всё, что нужно подставить перед публикацией, собрано одним списком в
[docs/LAUNCH.md](LAUNCH.md) — с путями к файлам и с тем, откуда брать
значения.

Демо на GitHub Pages публикует [.github/workflows/deploy.yml](../.github/workflows/deploy.yml):
собирает `dist/` без сервера. Боевая сборка — `deploy/` (Docker, Caddy). Заявки
с форм принимает свой сервер (`POST /api/leads`, хранение — `deploy/README.md`);
`server/leads/` — прежний приёмник, функция Яндекс Облака, в боевой сборке не
участвует.

Логотипы в списке интеграций принадлежат их правообладателям и используются
только чтобы обозначить, с какой системой идёт обмен.
