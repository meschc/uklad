# Как участвовать в разработке

Репозиторий закрытый (см. [LICENSE](LICENSE)), но правила в нём обычные: ветка,
понятный коммит, зелёные проверки, разбор изменений. Здесь собрано то, что
человек ищет в первый день, — как поднять, как назвать, что прогнать.

## Поднять у себя

```bash
nvm use            # версия лежит в .nvmrc, сейчас Node 26
npm ci             # ровно то, что в package-lock; npm install — только когда меняете зависимости
npm run dev
```

Откроется `http://localhost:5174` — витрина; демо WMS рядом, на
`http://localhost:5174/app/`. Порт закреплён (`strictPort`) не из вредности: в
`localStorage` этого адреса лежит план склада, с которым работают, и переезд на
соседний порт означал бы пустой склад. Бэкенда нет — данные живут в браузере, а
демо-склад подсевается при первом запуске.

Все команды — в таблице скриптов [README](README.md#скрипты).

## Ветки

```
feat/<коротко-о-чём>     новая возможность
fix/<коротко-о-чём>      исправление
refactor/<коротко-о-чём> перекладка без изменения поведения
docs/<коротко-о-чём>     только документация
```

От `main`, по-английски, через дефис: `feat/compare-panel`, `fix/scan-status`.
Одна ветка — одна тема. Ветка на три несвязанных правки разбирается втрое
дольше, чем три ветки по одной.

## Коммиты

```
<type>: <что изменилось>

<зачем, если из заголовка не видно>
```

Типы: `feat`, `fix`, `refactor`, `docs`, `test`, `chore`, `perf`, `ci`.
Заголовок — по-русски, в настоящем времени, без точки в конце, до 72 символов:
`feat: сравнение складов на витрине`. Тело — про причину, а не про диф: что в
коде изменилось, видно и так, а почему — уже нет.

Историю ведём по [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/):
заметное для пользователя изменение попадает в [CHANGELOG.md](CHANGELOG.md), в
раздел `[Не выпущено]`. Перекладки и правки формата — нет.

## Перед тем как отправить

Хуки прогоняют часть проверок сами: `pre-commit` — линтер и форматтер по
файлам в индексе, `pre-push` — типы и тесты. Полный круг, тот же что в CI:

```bash
npm run format:check && npm run lint && npm run typecheck && npm test && npm run build
```

Сборка здесь не формальность: `npm run build` дописывает предрендер и падает на
всём, что живёт только в браузере. Ожидаемый хвост вывода —
«Предрендер: 152 страниц, карта сайта на 76 адресов».

Сквозные тесты (`npm run test:e2e`) стоят отдельным заданием в CI; локально их
достаточно гонять, когда правка задела витрину, маршруты или вёрстку.

Обойти хук осознанно — `--no-verify`. Обойти CI нечем, и это правильно.

## Куда класть код

Подробности — в [CLAUDE.md](CLAUDE.md) и картах `docs/CODEMAPS/`. Коротко о
том, что чаще всего нарушают:

- **Слой данных.** Реактивное чтение — из стора (`useEditor`), команда или
  разовое чтение — через репозиторий (`src/lib/data/*`). Экран не пишет в
  `localStorage` сам: репозиторий — единственное место, знающее «где лежит»,
  и именно в нём появится `fetch`.
- **Строки.** Только через `useT()` (кабинет) или `c(ru, en)` (витрина). Ключ
  добавляется сразу в оба словаря — пропуск перевода не соберётся по типам.
- **Файлы.** 200–400 строк — норма, 800 — потолок. Большой экран режется на
  папку рядом с собой (`fulfillment/receiving/`, `editor/canvas/`), а не растёт.
- **Тесты.** Рядом с кодом, в `__tests__/`. Проверяются расчёты, которые
  ошибаются молча, и поведение экранов, которое ломается при перекладке.
  Компонентному тесту нужна первая строка `// @vitest-environment jsdom`.
- **Документация.** Правка, меняющая карту кода, меняет и карту:
  `docs/CODEMAPS/`. Архитектурное решение — короткая запись в `docs/adr/`.

## Разбор изменений

Смотрим на четыре вещи, в этом порядке: поведение (то ли делает), границы (что
будет на пустом, кривом и чужом вводе), читаемость (поймёт ли следующий) и
след в документации. Замечание формулируется как вопрос к коду, а не к автору.

Черновики, аудиты и планы сессий лежат в `docs/drafts/` и в репозиторий не
попадают — папка целиком в `.gitignore`. Это рабочая кухня, а не документация.
