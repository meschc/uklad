# Развёртывание Уклада на своём сервере

Инструкция для первого запуска, по шагам. На сервере будут работать две
вещи в Docker:

- **web** — Caddy: отдаёт сайт (витрину и кабинет `/app/`), сам получает и
  продлевает HTTPS-сертификат, ставит заголовки защиты;
- **api** — сервер заявок (`server/api`): принимает заявки с форм, кладёт их
  в базу, пересылает на почту и отправляет персональные демо-ссылки.

```
Браузер ──HTTPS──▶ web (Caddy, :443) ──▶ статика сайта
                         │
                         └── /api/*, /d/* ──▶ api (Node, :8080, наружу закрыт)
                                                 └── data/uklad.db (SQLite)
```

Сервер должен стоять **в России**: в заявках персональные данные, а ч. 5
ст. 18 152-ФЗ требует хранить их базу на территории РФ.

## Что нужно заранее

1. **Сервер (VPS)** у российского провайдера: Ubuntu 24.04, 1 ядро, 1–2 ГБ
   памяти, 20 ГБ диска. Этого с запасом.
2. **Доступ по SSH** — провайдер пришлёт IP-адрес и пароль root или попросит
   ваш SSH-ключ.
3. **Почтовый ящик домена** (например, Яндекс 360 для `u-klad.ru`) и
   «пароль приложения» для него — через него сервер шлёт письма.

## Шаг 1. Войти и закрыть сервер

```sh
ssh root@ВАШ_IP
```

Создайте своего пользователя и запретите вход по паролю (аудит 21.10):

```sh
adduser kir
usermod -aG sudo kir
mkdir -p /home/kir/.ssh && cp ~/.ssh/authorized_keys /home/kir/.ssh/ && chown -R kir:kir /home/kir/.ssh
```

Проверьте в **новом окне**, что `ssh kir@ВАШ_IP` пускает по ключу. Только
после этого закройте вход по паролю. Настройку кладём отдельным файлом, а не
правим основной: на Ubuntu 22/24 файл `50-cloud-init.conf` часто включает
пароль обратно и перекрывает правку основного конфига.

```sh
printf 'PasswordAuthentication no\nPermitRootLogin no\nKbdInteractiveAuthentication no\n' | sudo tee /etc/ssh/sshd_config.d/00-uklad.conf
sudo sshd -T | grep -Ei 'passwordauth|permitroot'   # должно быть «no» в обеих строках
sudo systemctl restart ssh
```

Файрвол и защита от подбора паролей:

```sh
sudo apt update && sudo apt install -y ufw fail2ban unattended-upgrades
sudo ufw allow OpenSSH && sudo ufw allow 80 && sudo ufw allow 443
sudo ufw enable
```

`unattended-upgrades` сам ставит обновления безопасности системы.

**Важно: Docker обходит ufw.** Порт, опубликованный в `compose.yml`
(`ports:`), открыт в интернет, даже если ufw его не разрешал. Наружу сейчас
открыты только 80 и 443 у Caddy. Не добавляйте `ports:` к сервису `api`; если
порт нужен для отладки, только так: `127.0.0.1:8080:8080`.

## Шаг 2. Поставить Docker

```sh
curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker kir
```

Выйдите (`exit`) и зайдите снова, чтобы группа применилась. Проверка:
`docker run --rm hello-world`.

## Шаг 3. Забрать код

```sh
cd ~ && git clone https://github.com/meschc/uklad.git && cd uklad/deploy
```

## Шаг 4. Настройки

```sh
cp .env.example .env
nano .env
```

Заполните `SITE_DOMAIN`, `ACME_EMAIL`, `SMTP_USER`, `SMTP_PASSWORD`,
`MAIL_TO`. Сохранить — `Ctrl+O`, `Enter`, выйти — `Ctrl+X`. Закройте файл от
чужих глаз:

```sh
chmod 600 .env
```

`.env` в git не попадает. Пароли не пересылайте в чаты и не вставляйте в
код — только сюда.

Папка для базы (сервер в контейнере работает не от root, а от пользователя
с номером 1000):

```sh
mkdir -p data && sudo chown 1000:1000 data
```

## Шаг 5. DNS

У регистратора (REG.RU) поменяйте A-записи `u-klad.ru` и `www.u-klad.ru` на
IP сервера. Пока сайт на GitHub Pages, это и есть момент переезда. Проверка:
`dig +short u-klad.ru` показывает новый IP (может занять до часа).

Хотите сначала проверить без переезда — заведите поддомен, например
`new.u-klad.ru`, впишите его в `SITE_DOMAIN` и направьте на сервер только его.

## Шаг 6. Запуск

```sh
docker compose up -d --build
```

Первая сборка — 3–5 минут. Затем:

```sh
docker compose ps                         # оба сервиса Up (healthy)
curl -s https://u-klad.ru/api/health      # {"ok":true}
docker compose logs -f api                # журнал сервера заявок, выход Ctrl+C
```

Откройте сайт, отправьте заявку с лендинга складов — письмо должно прийти на
`MAIL_TO`. Если в поле контакта была почта и вид заявки «демо», на неё
придёт персональная ссылка.

## Обновление сайта

```sh
cd ~/uklad/deploy && ./deploy.sh
```

Скрипт забирает код, делает копию базы, собирает образы с номером коммита и
ждёт, пока сервер ответит. База и сертификаты лежат вне образов и при
обновлении не трогаются.

## Откат

Новая версия сломалась — вернуть прошлую одной командой, за полминуты:

```sh
cd ~/uklad/deploy && ./rollback.sh
```

Прошлые образы лежат на диске (последние пять выкладок), поэтому ничего не
собирается заново. Повторный `./rollback.sh` уходит ещё на версию назад.

**Откат кода не откатывает схему базы.** Поэтому изменения базы делаем
только совместимыми с прошлой версией кода: добавить поле можно, удалить или
переименовать — нет (сначала код перестаёт им пользоваться, удаление — в
следующей выкладке). Если схему всё же поменяли несовместимо, откатываться
только вместе с базой, через `restore.sh`. Откатывается код, а не база: если новая версия испортила
данные, восстановите копию, которую `deploy.sh` сделал перед выкладкой
(`restore.sh`, раздел «Бэкапы»).

## Бэкапы

`backup.sh` делает целостный снимок базы, сжимает его и (если задан
`BACKUP_REMOTE`) отправляет на другую машину. Копия на том же сервере от
поломки сервера не спасает — задайте `BACKUP_REMOTE`.

Если копии уходят на чужую или облачную машину, шифруйте их: поставьте
`age` (`sudo apt install age`), на своём компьютере создайте ключ
`age-keygen -o uklad-backup.key` и впишите его публичную часть (`age1…`) в
`BACKUP_AGE_RECIPIENT` в `.env`. Закрытый ключ на сервере не храните: без
него копию не прочитает никто, включая того, кто взломал сервер.

Запустить руками: `./backup.sh`. Каждую ночь в 03:00:

```sh
crontab -e
# добавить строку:
0 3 * * * cd /home/kir/uklad/deploy && ./backup.sh >> /home/kir/backup.log 2>&1
```

Восстановление (текущая база не стирается, а откладывается рядом):

```sh
sudo ./restore.sh /var/backups/uklad/uklad-2026-11-01-0300.db.gz
```

Раз в месяц пробуйте восстановить копию — бэкап, который ни разу не
восстанавливали, бэкапом не считается.

## Мониторинг

Две линии, и нужны обе.

1. **Снаружи — UptimeRobot** (бесплатно): проверка `https://u-klad.ru/api/health`
   раз в 5 минут с уведомлением в Telegram. Только она заметит, что сервер
   выключен целиком.
2. **Изнутри — `watchdog.sh`**: тот же адрес плюс место на диске (тревога при
   заполнении больше 80 %). Пишет в Telegram один раз при поломке и один раз,
   когда всё снова в порядке.

Как подключить Telegram: напишите @BotFather, команда `/newbot`, получите
токен. Напишите своему боту любое сообщение и откройте
`https://api.telegram.org/bot<ТОКЕН>/getUpdates` — там будет `chat":{"id":…`.
Впишите `TG_BOT_TOKEN` и `TG_CHAT_ID` в `.env`, проверьте `./watchdog.sh` и
добавьте в `crontab -e`:

```sh
*/5 * * * * /home/kir/uklad/deploy/watchdog.sh
```

У контейнеров стоят пределы памяти и процессора, а журналы Docker ограничены
тремя файлами по 10 МБ: ни утечка памяти, ни разросшийся журнал не уронят
весь сервер.

## Что где хранится (152-ФЗ)

| Что                                 | Где                                        | Сколько                                                             |
| ----------------------------------- | ------------------------------------------ | ------------------------------------------------------------------- |
| Заявки (тема, текст, согласие)      | `data/uklad.db`, таблица `leads`           | `LEADS_RETENTION_DAYS`, по умолчанию 180 дней, потом сами стираются |
| Демо-ссылки (почта, срок, открытия) | там же, `demo_links`                       | до конца срока ссылки                                               |
| IP-адреса                           | нигде — только в памяти для лимита частоты | до перезапуска                                                      |
| Копии базы                          | `BACKUP_DIR` и `BACKUP_REMOTE`             | `BACKUP_KEEP_DAYS`                                                  |

Итого заявка живёт до 180 дней в базе и ещё до 30 дней в копиях — так и
указать срок в политике конфиденциальности.

Перед приёмом заявок нужно подать уведомление в Роскомнадзор об обработке
персональных данных (pd.rkn.gov.ru).

## Админка

Адрес — `admin.<домен>` (DNS: ещё одна запись A на тот же сервер). Видна
только с адресов из `ADMIN_ALLOW_IPS` в `.env`, остальным отвечает 404.

**Завести владельца** (один раз):

```sh
 docker compose exec api node api/src/admin/cli.js create-owner почта@домен
```

Пробел перед командой — чтобы она не легла в историю оболочки. Команда
печатает пароль и секрет для приложения кодов (Яндекс Ключ, Google
Authenticator) один раз: сразу перенесите их в менеджер паролей и приложение,
затем `clear`. **Не копируйте этот вывод в чат с ИИ, в заметки и в
мессенджеры.**

**Если адрес меняется** (мобильный интернет) — не открывайте админку всем, а
зайдите через SSH-туннель:

```sh
ssh -L 8081:127.0.0.1:8081 uklad@сервер
```

Для этого на время раскомментируйте в `compose.yml` у `api` строку
`ports: ["127.0.0.1:8081:8081"]` — порт будет слушать только сам сервер.

**Если вход закрыт.** Пять неудач с одного адреса закрывают вход с него на
15 минут (снимается и перезапуском `docker compose restart api`). Двадцать
неудач подряд закрывают аккаунт целиком, снять:

```sh
docker compose exec api node api/src/admin/cli.js unlock почта@домен
```

## Дальше: проверочный сервер и Postgres

Пока на сервере только заявки, этого хватает. Когда кабинет переедет на
сервер (`support/data-architecture.md`), до первых клиентов добавить:

- **Проверочный сервер (staging).** Второй маленький VPS или второй
  `compose` на том же сервере с доменом `staging.u-klad.ru` и своим `.env`.
  Каждая выкладка сначала идёт туда, потом в бой. Данные на нём — копия боевой
  базы с заменёнными почтами и именами, а не живые.
- **pgBackRest для Postgres.** Ночная полная копия плюс непрерывный журнал
  (WAL), чтобы восстановить базу на любую минуту, а не только на ночь.
  Копии — в S3 в РФ у другого провайдера, зашифрованные. Раз в месяц
  автоматическое восстановление на пустую базу с отчётом.

## Если что-то не так

- **Сертификат не выдаётся** — DNS ещё не указывает на сервер или закрыт
  порт 80. `docker compose logs web`.
- **Заявка не уходит, на сайте «не вышло»** — `docker compose logs api`:
  чаще всего неверный пароль приложения почты. Заявка при этом уже в базе.
- **`permission denied` на `/data`** — не выполнен `chown 1000:1000 data`.
- **CSP.** Заголовок политики пока в режиме «только отчёт». Неделю после
  запуска смотрите консоль браузера на сайте; если там нет нарушений, в
  `Caddyfile` замените `Content-Security-Policy-Report-Only` на
  `Content-Security-Policy` и перезапустите `docker compose up -d --build`.
