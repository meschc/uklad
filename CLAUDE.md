# Уклад — карта проекта

Веб-прототип визуальной раскладки склада: 2D-редактор плана мезонина, таблица
номенклатуры, тепловая карта, фулфилмент-контур (приёмка / задания / сборка).
Фронтенд без backend — всё живёт в `localStorage`.

## Стек

React 18 + TypeScript + Vite 6 · Zustand 4 (`persist`) · Tailwind + shadcn/ui
(Radix) · `lucide-react` (иконки) · `xlsx` (SheetJS, импорт) · `three` (3D,
сейчас скрыт флагом `SHOW_3D`) · `leaflet` (карта склада).

Команды: `npm run dev` (порт 5174, strictPort), `npm run build`, `npm run lint`
(= `tsc -b --noEmit`), `npm test` (Vitest, разово), `npm run coverage`.

## Ключевые решения

- **Данные только в localStorage**, ключ `uklad-store-v1`, версия персиста 8.
  Второй «аккаунт» (продавец) — это режим просмотра тех же данных, а не сеть.
- **Весь доступ к данным — через `lib/data/*Repository.ts`**, а не напрямую в
  localStorage. Сегодня внутри тот же Zustand, сигнатуры уже асинхронные:
  когда придёт Supabase, меняется реализация репозитория, а не экраны. Реактивный
  рендер по-прежнему подписан на стор — он и есть локальный кэш. На границе
  хранилища (`merge` в `store/index.ts` → `data/sanitize.ts`) каждая доменная
  запись проходит проверку формы: битая запись теряется одна, а не роняет
  приложение.
- **Роль читается только из сессии** (`selectRole(s)` → `session.user.role`).
  Отдельного поля `currentRole` больше нет: `User`/`Session` описаны так, чтобы
  стать настоящей авторизацией без правки экранов. Реального логина по-прежнему
  нет — токен локальный мок.
- **Экран падает один**: каждый вид обёрнут `ErrorBoundary` (ключ по виду, см.
  `App.tsx`). Изолируем сбой рендера, а не данные: единый `buildOccupancy`
  остаётся один на всех.
- **План условный**: координаты модулей — в КЛЕТКАХ сетки, реальные см живут
  отдельными полями и на визуальный масштаб не влияют.
- **«Пол как проход»**: объектов-проходов больше нет, зазор между линиями
  секций и есть проход (миграция v1→v2 вырезает `type: "aisle"`).
- **Связанные этажи** (`Floor.aliasOf`): этаж-алиас зеркалит раскладку
  источника, правки уходят в источник — см. `resolveFloor` / `mutateActiveFloor`.
- **Единый alert-паттерн** «на полке товар» (`GoodsConflictDialog`): правку
  плана не запрещаем, а спрашиваем, что делать с товаром.
- **Сканирование — HID** (сканер «печатает» код + Enter), без камеры.
- **Приёмка идёт от тары**: паллета (необязательно) → открыть тару → товар →
  закрыть тару и поставить на место. Ярлыки тары печатаются заранее на экране
  «Ярлыки», приёмка их только сканирует.
- **Одна высота на строку интерфейса**: контролы только трёх ступеней —
  32 / 36 / 40 px (`Button`, `Input`, `Segmented`). Любые «кнопки-табы» — через
  `ui/segmented.tsx`, свои наборы `bg-muted p-0.5` не собираем.
- **Профиль правится по одному полю**: карандаш открывает одну строку,
  галочка сохраняет её (Enter/Escape тоже работают). Почта меняется только
  через подтверждение кода, реквизиты компании приходят по ИНН сами — кнопки
  «подтянуть» нет.
- **Регистрация — почта и пароль**: имя и компания живут в профиле, а не в
  пропуске в систему. Роль (склад/продавец) в форме остаётся: она решает, куда
  человек попадёт после входа.
- **Заявки группируются по назначению**: одна машина увозит всё, что едет
  одному получателю; дата отгрузки — подпись к группе, а не её ключ.
- **Нагрузка персонала — по фактам, а не по ощущениям** (`staffWorkload`):
  приёмки, принятые единицы, отгрузки и дата последней операции берутся из
  `ReceivingEvent.staffId` и `Shipment.staffId`. Сборка персонально не
  подписывается, поэтому в нагрузку не входит — числа, которого нет в данных,
  в таблице быть не должно.
- **Паспорт склада — один экран на две роли** (`WarehouseSpecScreen`, вид
  `spec`): режим работы и заезд, условия хранения (температура, влажность),
  противопожарная категория и оснащение, ограничения и состояние. Склад правит
  поля на месте, продавец видит те же данные на чтение — второй «витрины»
  нет по той же причине, что и у таблицы номенклатуры.
- **Машину может назвать продавец**: поле в заявке (`vehicle`), склад видит его
  подставленным в диалоге погрузки и только подтверждает.
- **У продавца два направления, а не одно**: «В заявку» — забрать со склада,
  «Везу товар» (`SupplyDialog`) — привезти на склад. Второе создаёт обычную
  ожидаемую поставку (`createExpectedShipment`, источник `manual`), которую
  склад принимает построчно со сверкой план/факт; продавец видит её прогресс
  блоком «Еду на склад».
- **«Собрана» и «отгружена» — разные статусы**: снятое с полок ещё не уехало.
  Погрузка — отдельный шаг (`shipRequests`, `ShipDialog`): собранные заявки
  одного назначения уезжают рейсом (`Shipment`) с номером машины и
  ответственным. Продавец в своих заявках видит «Уехало {дата} · машина» —
  это и есть отчёт подрядчика о выполненной работе.
- **Роль продавца — режим чтения**: те же план, номенклатура и персонал, но без
  структурных правок — ни «плюсиков» продолжения ряда, ни контекстного меню,
  ни горячих клавиш, ни undo, ни создания складов. Проверка роли — в трёх
  местах: `useShortcuts`, `Canvas`, `Dashboard`; экраны прячут своё через
  `readOnly = currentRole === "seller"`. Заявка набирается списком позиций на
  одну машину.
- **Одна таблица номенклатуры на обе роли**: у продавца на вкладке «Остатки»
  та же `TableScreen`, только без складских действий и с «В заявку». Своя
  урезанная копия таблицы разъезжается с настоящей на первой же правке.
- **Запрет висячих строк**: короткие слова и числа склеиваются неразрывным
  пробелом в `i18n.ts` (`noOrphans`), последнюю строку абзаца балансирует CSS
  (`text-wrap: pretty` / `balance` в `index.css`). Работают только вместе.
- **Кроссдокинг и дропшиппинг — две стороны одного «товара, которого ещё нет»**:
  у поставки с `crossDock` шага «место» нет вовсе, принятое сразу закрывает
  ждущие заявки (`applyCrossDock`) и в занятость не попадает — оно физически не
  хранится. Обратно: заявка бронируется под ещё не приехавшую строку поставки
  (`reservedFor` / `reservedShipmentId`); свободное для брони — это ожидаемое
  минус принятое минус чужая бронь, иначе одну коробку продадут дважды.
- **У набора нет своего остатка** (`Kit`, `kitAvailability`): он всегда
  считается по компонентам. Заявка на набор — это несколько строк с общим
  `kitId`, и на «Сборке» они показываются одной подзадачей.
- **Приоритет отбора живёт на полке** (`ShelfConfig.pickPriority` / `pickable`):
  меньше число — ближе к проходу и раньше в автоподборе; `pickable: false`
  исключает полку из подбора, не трогая то, что уже лежит.
- **Витрина — отдельный проект** (`site/`): публичная страница со статусами
  работ, роадмапом и журналом обновлений, своя сборка и свои зависимости.
  Общее с приложением — палитра: `site/src/tokens.css` генерируется из
  `src/index.css` тем же `npm run tokens`, что и токены для Figma. Содержимое
  роадмапа статично (`site/src/data/roadmap.ts`) — бэкенда и админки нет
  намеренно, правка роадмапа это коммит. Голос за пункт живёт в браузере
  посетителя и прибавляется к числу из файла.
- В dev доступен `window.__uklad` — стор целиком, для проверки сценариев из
  консоли вместо ручной пантомимы мышью.

## Тесты (`src/**/__tests__/`)

Vitest, окружение node — React не тестируется, проверяются расчёты, которые
ошибаются молча: неверный ответ выглядит как обычный, и заметить его можно
только по расхождению через неделю.

```
lib/__tests__/fixtures.ts            заготовки доменных объектов
lib/__tests__/placement.test.ts      занятость ячеек, подбор места, габариты
lib/store/__tests__/harness.ts       стенд среза: zustand без persist и посева
lib/store/__tests__/requests.*.test  бронь под поставку, кроссдокинг, сборка
```

У витрины свой прогон (`cd site && npm test`): группировка колонок, прогресс
вех, фильтр, подписи дат и проверки самих данных роадмапа — уникальность
идентификаторов, привязка к вехам, дата выхода только у готового.

Стор целиком в тестах не поднимается: `store/index.ts` при импорте читает
localStorage и сеет демо-историю. Срез собирается стендом поверх состояния,
которое задаёт сам тест, соседние срезы при нужде подменяются заглушками.

## Стор (`src/lib/store/`)

Один объект состояния, собранный из срезов в `index.ts`. Срез = файл
`*.slice.ts` c `createXxxSlice: SliceCreator<XxxSlice>`; форма всех срезов —
в `state.ts`, общие помощники — в `helpers.ts`, демо-данные — в `seed.ts`.

| Файл | За что отвечает |
|---|---|
| `account.slice` | аккаунт, профиль, список складов, навигация по экранам |
| `floors.slice` | этажи, тиражирование, связь этажей |
| `catalog.slice` | товары, поиск, доп.поля категорий |
| `placement.slice` | размещения товара, конфликт «на полке товар» |
| `modules.slice` | модули на плане, выделение, буфер обмена |
| `shelves.slice` | полки/ячейки, библиотеки шаблонов |
| `rows.slice` | ряды, адресация, автонумерация |
| `view.slice` | режим экрана, камера, тосты |
| `onboarding.slice` | разовые подсказки |
| `history.slice` | undo/redo (снимки пишутся подпиской, не в редьюсерах) |
| `fulfillment.slice` | поставки (в т.ч. кроссдок), приёмка, коробки, паллеты |
| `requests.slice` | заявки продавца, отгрузка рейсов, бронь под поставку |
| `session.slice` | сессия и роль пользователя (`selectRole`) |
| `staff.slice` | персонал склада, ответственное лицо, партнёры-продавцы |
| `integrations.slice` | настройки подключений к внешним системам |
| `labels.slice` | шаблоны наклеек: размер печати и набор реквизитов |

Правила: мутации иммутабельные; правка активного этажа — только через
`mutateActiveFloor`; в многошаговых действиях перечитывать `get()` на каждой
итерации (иначе двое уедут в одну ячейку).

## Что легко сломать

- `buildOccupancy` (`placement.ts`) — единственный источник занятости для
  тепловой карты, `AssignDialog` и проверки конфликтов. Товар может лежать
  напрямую в ячейке ИЛИ внутри коробки с адресом; учитывать оба пути.
- `formatAddress`/`parseAddress` должны оставаться обратными друг другу —
  ярлыки ячеек печатаются тем же форматом, что показан в интерфейсе.
- Снимок этажа-алиаса обязан быть стабильным по ссылке (`aliasViewCache`),
  иначе `useSyncExternalStore` зациклит рендер.
- `detectRows` (`numbering.ts`) — ряд это ПАРА линий стеллажей по обе стороны
  прохода (зазор 1–3 клетки), а линии вплотную (нулевой зазор) — это спины
  соседних рядов. Правка этой эвристики ломает адресацию всего склада.
- `partialize` в `store/index.ts`: новое доменное поле нужно явно добавить,
  иначе оно не переживёт перезагрузку.
- `updateWarehouse` (`account.slice`) собирает склад из ПЕРЕЧИСЛЕННЫХ полей —
  новое поле склада нужно дописать туда явно, иначе оно молча не сохранится
  (на этом уже терялся `storageRatePerCell`). Поля, которые можно стереть,
  проверяются через `"поле" in patch`, а не по значению.
- Проверки формы в `data/guards.ts` — не схема на каждое поле, а «похоже ли это
  на запись». Слишком строгая проверка выкинет живые данные пользователя
  молча — предупреждение в консоль обязательно.
- Посев (`seed.ts` + `seedHistory.ts`) применяется ТОЛЬКО при первом запуске —
  иначе он затирал бы работу пользователя. Увидеть обновлённые демо-данные
  можно кнопкой «Профиль → Демо-данные → Загрузить заново»: она чистит
  `PERSIST_KEY` и перезагружает страницу.
- `qrcode-generator` по умолчанию режет байты строки в `charCode & 0xff` и
  ломает кириллицу. В `lib/qr.ts` кодировщик подменён на UTF-8 — не убирать.
- Ноль и «ещё не считали» в документах — разные вещи: непринятая строка листа
  приёмки уходит на бумагу ПУСТОЙ клеткой, а не нулём с расхождением на всю
  партию (`documents.ts`, `DocumentSheet`).

## Соглашения

Комментарии и UI-тексты — по-русски; строки интерфейса только через `i18n.ts`
(ru + en парой). Файлы 200–400 строк, максимум ~800. Иконки — `lucide-react`.
Новый диалог-предупреждение — переиспользовать `GoodsConflictDialog`, а не
изобретать свой.
