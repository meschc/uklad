# server/db — схема Postgres

Основа будущего сервера кабинета: компании, роли, сотрудники, склады, договоры
склад ↔ селлер, товары, остатки, брони и журнал остатков. Почему так —
`docs/adr/0009-postgres-rls.md`; полная архитектура — в
`support/data-architecture.md` (папка проекта), правила изоляции — раздел 5а.

## Как устроено

- **Две роли.** `uklad_owner` владеет таблицами, под ней идут только миграции.
  `uklad_app` — роль приложения: не владелец, без `BYPASSRLS`, без `DELETE`.
- **Компания в каждой транзакции.** Сервер начинает транзакцию и ставит
  `SELECT set_config('app.org_id', '<из сессии>', true)`. Не поставил — запрос
  не видит ни строки. `SET` без `LOCAL` не использовать никогда.
- **RLS на каждой таблице** `uklad.*`, с `FORCE`. Тест `schema.test.js`
  проверяет это обходом схемы: новая таблица без `org_id NOT NULL`, RLS или
  FORCE роняет CI.
- **Удаления нет.** «Удалить» — поставить `deleted_at`. Права `DELETE` у
  приложения нет вовсе.
- **Селлер видит только свой товар** (`seller_org_id`) и только пока договор
  с этим складом активен. Владельца товару назначает склад.
- **Бронь — функцией `uklad.reserve`**, а не двумя запросами из кода: замок
  на строку остатка и ключ повтора (`Idempotency-Key`) внутри.

## Команды

```sh
npm ci
# Разово на новом сервере, под суперпользователем (пароли — из .env):
psql -v owner_pw="…" -v app_pw="…" -f init.sql
# Каждая выкладка, под uklad_owner:
DATABASE_URL=postgres://uklad_owner:…@localhost/uklad npm run migrate
# Тесты: нужен любой Postgres 16 и суперпользователь для подготовки базы.
PG_ADMIN_URL=postgres://postgres:postgres@localhost:5432/postgres npm test
```

Тесты создают свою базу `uklad_test_*` на каждый файл и удаляют её в конце.
В CI это отдельное задание «Изоляция компаний (Postgres)».

## Новая миграция

Файл `migrations/NNN_что_делает.sql`, следующий номер. Применённый в бою файл
не правят — пишут следующий. Колонку не удаляют сразу: сначала код перестаёт
ею пользоваться, потом отдельной миграцией. Новая таблица — сразу с
`org_id NOT NULL`, `ENABLE` + `FORCE ROW LEVEL SECURITY`, политиками и
`GRANT SELECT, INSERT, UPDATE` для `uklad_app`.

## Чего ещё нет

Матрица доступа через API (5а, тест 1) — появится вместе с API. Вход,
план склада (ячейки таблицей), приёмка, сборка, заявки, чат, события
аналитики — следующие миграции по порядку работ.
