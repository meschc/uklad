# server/db — схема Postgres

Основа будущего сервера кабинета: компании, роли, сотрудники, склады, договоры
склад ↔ селлер, товары, остатки, брони и журнал остатков. Почему так —
`docs/adr/0009-postgres-rls.md`; полная архитектура — в
`support/data-architecture.md` (папка проекта), правила изоляции — раздел 5а.

## Как устроено

- **Две роли.** `uklad_owner` владеет таблицами, под ней идут только миграции.
  `uklad_app` — роль приложения: не владелец, без `BYPASSRLS`, без `DELETE`.
- **Компания в каждой транзакции.** Сервер начинает транзакцию и ставит
  `SELECT set_config('app.org_id', '<из сессии>', true)`. Не поставил — запрос
  не видит ни строки. `SET` без `LOCAL` не использовать никогда.
- **RLS на каждой таблице** `uklad.*`, с `FORCE`. Тест `schema.test.js`
  проверяет это обходом схемы: новая таблица без `org_id NOT NULL`, RLS или
  FORCE роняет CI.
- **Удаления нет.** «Удалить» — поставить `deleted_at`. Права `DELETE` у
  приложения нет вовсе.
- **Селлер видит только свой товар** (`seller_org_id`) и только пока договор
  с этим складом активен. Владельца товару назначает склад.
- **Бронь — функцией `uklad.reserve`**, а не двумя запросами из кода: замок
  на строку остатка и ключ повтора (`Idempotency-Key`) внутри.

## Главное условие изоляции

Вся изоляция держится на том, что `app.org_id` ставит **только серверный код
из сессии**. Отсюда правила для каждого модуля:

- только параметризованные запросы (`$1`), никакого SQL, собранного из ввода;
- `set_config`, `SET`, `RESET` никогда не принимают значения от пользователя;
- `orgId` из запроса браузера — подсказка, сверить с сессией (5а, правило 2).

Одна SQL-инъекция — и RLS обходится сменой компании прямо в запросе.

## Вход (миграция 004)

Учётные записи, сессии, бейджи и неудачные входы лежат в схеме `auth`, к
таблицам которой у приложения доступа нет — только к функциям. Главная —
`auth.resolve(токен, компания, склад, …)`: она сама ставит `app.org_id`,
`app.member_id` и `app.warehouse_id`, если у сессии есть живое членство.
Бейдж выдан на один склад и в другой не пускает. Сервер — `server/api/src/cabinet/auth.js`.

## Команды

```sh
npm ci
# Разово на новом сервере, под суперпользователем (пароли — из .env):
psql -v owner_pw="…" -v app_pw="…" -v notifier_pw="…" -f init.sql
# Каждая выкладка, под uklad_owner:
DATABASE_URL=postgres://uklad_owner:…@localhost/uklad npm run migrate
# Тесты: нужен любой Postgres 16 и суперпользователь для подготовки базы.
PG_ADMIN_URL=postgres://postgres:postgres@localhost:5432/postgres npm test
```

Тесты создают свою базу `uklad_test_*` на каждый файл и удаляют её в конце.
В CI это отдельное задание «Изоляция компаний (Postgres)».

## Новая миграция

Файл `migrations/NNN_что_делает.sql`, следующий номер. Применённый в бою файл
не правят — пишут следующий. Колонку не удаляют сразу: сначала код перестаёт
ею пользоваться, потом отдельной миграцией. Новая таблица — сразу с
`org_id NOT NULL`, `ENABLE` + `FORCE ROW LEVEL SECURITY`, политиками и
`GRANT SELECT, INSERT, UPDATE` для `uklad_app`.

## Чат (миграция 006)

Диалог — участники и сообщения, а не пара «склад ↔ селлер»: общий чат
нескольких людей устроен так же, как разговор вдвоём. Изоляция в два слоя:
диалог видят только компании из `org_ids` (своя и вторая сторона договора), а
сообщения — только участники. Своих людей в диалог добавляет только своя
компания, писать нужно право `chat.use`, после закрытия договора история
читается, но новых сообщений нет. Связи строк (диалог, автор, участник) после
вставки не меняются — это держат триггеры `chat_*_frozen`. Доставка в
реальном времени (Centrifugo) — в API, не здесь.

## Уведомления о непрочитанном (миграция 007)

Телеграм-бот и письмо для тех, кто отошёл от кабинета. Привязка Телеграма —
одноразовым кодом из ссылки на бота (в базе хэш, 10 минут), номер чата и
почта лежат в закрытой схеме `auth`. Кому и о чём пора сказать, решает
`auth.chat_due`: участник диалога, уведомления не выключены, сообщение
не прочитано дольше заданного; текст — только при `notify_preview`. Письмо —
только на подтверждённую почту.

Рассылка одна на сервер и читает поверх компаний, поэтому правило
`notifier_read` открывает чтение только роли владельца и только пока функция
рассылки сама поставила `app.notifier`. Приложению флаг ничего не даёт — это
проверяет тест в `chat.test.js`. Сами функции рассылки и вебхука бота
выданы только третьей роли, `uklad_notifier` (init.sql), со своим
подключением `NOTIFIER_DATABASE_URL`: SQL-инъекция в маршруте кабинета не
дотянется до чужой переписки.

## Чего ещё нет

Матрица доступа через API (5а, тест 1) — появится вместе с API. Вход,
план склада (ячейки таблицей), приёмка, сборка, заявки, события
аналитики — следующие миграции по порядку работ.
